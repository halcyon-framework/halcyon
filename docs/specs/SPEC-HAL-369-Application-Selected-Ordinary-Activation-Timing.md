# SPEC-HAL-369: Application-Selected Ordinary Activation Timing

**Author:** JC
**Status:** Draft / Proposed — INACTIVE, NOT ACCEPTED, NOT BINDING.
**Date:** 2026-10-19.
**Source revision:** 13af31cc253812316fca9c75974d69d5517d0edf.
**Implementation:** absent; no public timing API exists at this revision.
**Scope:** explicit App-selected Press/Release for admitted ordinary discrete actions.
**Acceptance authority:** JC alone; decisions pending in §11.

## 1. Problem and authority boundary

Button currently commits on pointer/key release; Checkbox and in-window menus commit on pointer release but their current keyboard paths commit on Down. There is no shared public timing selection. A consumer cannot lawfully add a product event router to make these controls uniformly activate on Press.

HAL-112/HAL-111/HAL-122 contain release obligations or inconsistent keyboard wording. Binding HAL-222 prohibits pointerDown activation and requires a new SPEC for extensions; Binding HAL-223 also requires a new SPEC. This is that proposed extension, not permission to bypass those requirements. Until JC explicitly accepts it and the exact §9 qualifications, all current authority retains its current status/effect and runtime work remains blocked. Approval to draft, review, a source commit or green tests is not adoption.

The proposal centralizes only the timing contract. Existing widget/menu/action/phase authorities remain their owners. It neither replaces those SPECs nor adopts their unrelated Design/Draft provisions,363/364 or another authority package.

## 2. Proposed eligible scope

**INV-OAT-SCOPE:** An ordinary discrete activation emits one existing primary action, boolean toggle, or command intent. It does not mean every Down/Up-driven operation.

The initial reviewed consumers are both public Button forms, Checkbox, and actionable entries in framework-rendered menus, through their existing emission and action owners. This is an explicit bounded inventory, not an automatic exception for every Category-A or composite control; another control requires admission under its own governing contract. Structural menu rows, separators, submenu opening/navigation, menu-trigger opening/dismissal and hover are not ordinary command activations merely because they receive input. A row with ambiguous command-vs-submenu intent requires its existing owner to declare the operation; the framework must not guess.

The proposal does not redefine:

- continuous drag/slider/range gestures, whose completion still occurs at valid release;
- spinner stepping/repeat, embedded text edits, value confirmation or text/IME commit;
- Category-K recording, physical training responses or shortcut bindings;
- RadioGroup's separately authorized mouseDown selection, keyboard target/navigation or non-mouse policy;
- direct programmatic commands, which remain explicit existing commands and do not wait for invented Up events;
- confirmation, validation, safety or permission gates. Selecting Press cannot bypass a gate or transform opening a confirmation into executing its confirmed command.

No additional semantic events, Widget instances, focus/capture owner, action registry, timing clock or renderer feature is proposed.

## 3. App policy and publication

**INV-OAT-POLICY:** The proposed public policy is typed Press or Release, owned by an App. Absence of an override is a distinct configuration condition, not a third timing or keyboard-authority mode. Recommended compatibility: absence inherits the current control/modality timing; explicit selection governs every eligible, supported consumer in its advertised scope.

Inheritance preserves timing choices, not known violations of existing once-only/repeat/disabled/identity laws. In particular, current Checkbox/menu keyboardDown behavior is implementation evidence, not adoption of contradictory release clauses or permission for repeat toggling. No blanket legacy-conformance claim is made.

The initial declaration must be installed before first input in every supported App runtime/domain. Runtime requests use the existing lawful App/deferred owner. They publish after the current qualified input batch, without changing already routed events; subsequent fresh admissible Downs observe the admitted successor policy. An active cycle keeps its captured timing. No second event scheduler or product route is introduced.

Request/readback must distinguish the requested override, pending/admitted/rejected/superseded disposition, currently published override, supported scope and effective inherited or explicit timing where queried. If pending requests replace each other before publication, the displaced request must be observably superseded. A rejected request changes neither published policy nor active cycles. Publication for one App must not partially expose different revisions to that App's affected domains; another App retains its independent policy.

A missing runtime/backend capability is an explicit admission/result, never a stored Press setting whose eligible consumer silently behaves as Release. Clearing the override restores inheritance for future cycles only. Existing UiInteractionPolicy is orthogonal: PointerDriven still prevents automatic UI keyboard delivery outside actual Capture.

No Rust type/method signature is claimed to exist or prescribed by this Draft. Implementation names, storage and transport design remain the executor's responsibility after normative acceptance.

## 4. Origin, latch and matching

**INV-OAT-ORIGIN:** A cycle starts only at an admitted original initial nonrepeat Down on a live eligible target. An already consumed/reserved event, hover, focus change, repeat, standalone Up or replay cannot create one.

Before possible emission, the existing owner must bind the cycle to:

- the owning App, interaction domain/window and live widget mount identity;
- the actionable subtarget's stable identity and declared command/binding identity when provided, not a menu row index or callback allocation address;
- the admitted timing/policy revision;
- the originating pointer/button/session or originating keyboard key/press identity.

Reuse existing qualified input/identity owners; this is not a second provenance registry. Ordinary keyboard dispatch currently loses key/repeat context at on_keyboard_activate; an implementation must close that actual seam rather than infer it later from current focus or a timer.

Matching uses original input identity, including the framework's admitted logical-key alias mapping, not whichever activation key happens to go Up. Unknown physical identity remains unknown; it must not be replaced with an invented physical key. Only an unambiguous pairing provided by the admitted input contract may complete Release.

Recommended keyboard concurrency rule: one ordinary keyboard activation cycle per current domain/owner. The first admitted activation Down owns it; repeats and other mapped activation-key Downs do not re-arm it while held. A different keyUp neither commits nor completes it. A fresh eligible cycle requires fresh input after terminal settlement. This does not seize arbitrary keys, change reserved bindings or turn the control into a keyboard-Capture owner. Pointer and keyboard cycles remain separate; cancellation of one channel does not cancel the other unless an existing shared owner/domain/focus boundary actually invalidates both.

Multi-click classification cannot create a second activation from one physical Down. Distinct physical click cycles may each activate once. No stale completion may follow a replacement widget, reused NodeId or changed declared command binding. Reordering an unchanged stable menu item alone must not substitute another item's action. A same-owner callback implementation refresh is not by itself proof of a different logical action: the framework must not inspect closure meaning or use allocation addresses as semantic identity. Applications replacing the logical action must use an owner-declared action/target replacement boundary; hidden semantic changes cannot be inferred.

## 5. Timing and observable lifecycle

**INV-OAT-ONCE:** Each admitted ordinary cycle emits at most one existing action/toggle/intent, including its associated binding publication. The one logical activation may deliver its currently declared callback and binding publication, each once; neither existing output is dropped or duplicated by policy selection. Consumption must be recorded before invoking a callback capable of requesting owner removal or another action. The callback cannot be re-fired by its own lifecycle cleanup.

| Observed input/boundary | Explicit Press | Explicit Release |
| --- | --- | --- |
| Initial admissible nonrepeat Down | Emit once immediately through the existing semantic/action path; mark committed. | Arm without emission. |
| Repeat or duplicate delivery | No additional emission or rearm. | No additional emission or rearm. |
| Matching admissible Up on the still-valid target | Cleanup only; no second action. | Emit once only if the original arm survives; then cleanup. |
| Nonmatching key/button Up | No action; it cannot complete this activation. | No action; it cannot complete this activation. |
| Observed exit, cancel, disabled/unavailable target, invalid scope/domain, relevant focus/Capture loss or owner/declared-command replacement | Retire the cycle; committed action remains committed. | Retire the arm without action; reentry cannot rearm it. |
| Policy publication during a cycle | Keep the latched choice; no extra emission. | Keep the latched choice; no early or duplicate emission. |

Release eligibility requires a valid Down, matching Up, the same still-live action target, current input/domain eligibility and admitted current hit geometry for pointer release. Keyboard Release additionally requires the original owner to remain the lawful eligible activation target. Merely focusing another control cannot move the pending activation to it.

In this proposal, an observed exit is an exit/cancellation fact admitted for that cycle through the existing normalization/routing/capture ingress and evaluated against current canonical owner-supplied hit geometry. It does not mean that a control receives every raw sample, and introduces no region, trajectory or new gesture API.

**INV-OAT-CANCEL:** Cancellation is terminal for pending activation. A later Up, repeat, focus restoration or reentry cannot revive it. A committed Press cannot be rolled back by later exit/cancel. Cleanup never emits a compensating toggle/undo. Existing transient press/hover feedback and capture cleanup still finish through their owners, even though semantic emission may already have happened.

A required intermediate cancellation fact must not be erased by input coalescing and then treated as permission to commit. Preserve such facts through the existing normalization/routing owner when needed; this does not prescribe replay of every raw sample, add a gesture class or claim that current source already proves complete cancellation coverage. No inferred trajectory or synthetic input may substitute for an actual observation.

Existing capture teardown remains authoritative. For example, the current ordinary pointer path may cancel capture on a different button's Up. The timing contract must treat actual cancellation as terminal and must not turn that foreign Up into activation; it does not silently promise a new multi-button capture policy. Existing continuous gesture and relative-lock ownership are unchanged.

## 6. Eligibility and ownership

**INV-OAT-AUTHORITY:** Input normalization/routing owns original input and admission; a live control/menu owner maps admitted activation into its existing semantics; the existing action/callback/binding owner performs emission. Checkbox's semantic transition function still consumes its existing Activate/Cancel/FocusGain/FocusLoss events; this proposal creates no raw-input, timing or focus authority in that reducer and no extra Checkbox event. MenuSurface retains menu input/lifetime ownership and emits the existing item intent; command execution remains outside MenuItem/MenuSurface.

Eligibility must be checked before Press emission and again before a pending Release emission. It includes existing disabled declarations, modal/domain/window availability, input consumption/reservations, focus/Capture policy and live action identity. Disabling/retiring an eligible target synchronously prevents pending emission; re-enabling does not re-arm it. Button currently has no disabled property and publishes enabled:true; this proposal does not fabricate such an API or claim a tested Button-disable transition. Existing Checkbox/menu disabled behavior must remain absolute; extending Button's independent enable/disable surface requires an explicit owner scope.

Callbacks may request AppState/navigation/structural changes only through the current Context/deferred machinery. Press changes the emission point, not the mutation phase. After a callback or deferred boundary, any later work must revalidate identity instead of dereferencing a stored widget/callback reference. No pending activation may migrate to a replacement mount or declared action binding.

Menu dismissal following successful activation remains the existing menu-owner consequence and cannot expose the same Up to activate underlying UI. Menu input paths, including Screen-level context-menu keyboard handling, must consume the same admitted timing; a product callback cannot supply the missing policy. Programmatic commands remain separate from a physical activation lifecycle and must not synthesize key or pointer events.

## 7. Supported and qualified target boundaries

**INV-OAT-READINESS:** Contract acceptance, implementation conformance and target readiness are separate. Any public request/readback must describe the actually supported runtime/channel scope.

Recommended initial scope is framework-rendered ordinary controls and menu actions through their admitted mouse/touchpad-pointer and keyboard routes, in both supported canonical and dedicated App lifetimes. A runtime lacking transport/publication cannot silently ignore the override; it must report lack of capability before claiming the requested policy is admitted there.

Current ordinary Raw pointer transport does not carry native contact IDs and current routing uses MOUSE. Native touch/pen/multiple-contact parity is therefore not established. Accepting this Draft must not be described as implementing or verifying touch. If JC requires native contact support in the first runtime unit, that unit must include real admitted contact identity/transport and its causal proof; MOUSE substitution is not parity.

Native macOS main-menu tracking remains separately owned under HAL-333 §4. In-window policy does not claim control over AppKit's tracking phase. Native menu commands may retain their existing explicit normalized command delivery, but are outside the proposed selectable physical Press/Release scope until separately admitted. A request that purports to cover unsupported native tracking must reject that scope explicitly; it cannot report universal timing selection. These are exact scope qualifications for JC, not unilateral reductions of the requested outcome.

No native GUI/automation proof is claimed in this proposal.

## 8. Compatibility and consumer boundary

Unconfigured applications retain their existing modality/control timing, subject to already-required safety invariants. Explicit Press and explicit Release are reusable framework capabilities, not app-specific skins, event handlers or route interceptors. Selecting either cannot enable keyboard UI in PointerDriven, turn display-only/structural entries into commands, or change editor/continuous interactions.

The requesting product intends an explicit Press default and a user-selectable Release alternative only after the framework capability is admitted and implemented. The product separately owns its Configuration UI and actual supported session/persistence behavior. This Draft implements or claims none of that configuration, restart persistence or product adoption.
